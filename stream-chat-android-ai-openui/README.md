# OpenUI

`stream-chat-android-ai-openui` brings [OpenUI](https://github.com/thesysdev/openui) to Stream's AI components: OpenUI Lang is the compact, streaming-friendly language models answer in to describe generative UI. The module plugs into the generative UI layer of `stream-chat-android-ai-compose`.

## Show replies in a conversation

`OpenUIRenderer` plugs OpenUI into the generative UI of `stream-chat-android-ai-compose`: give it to the conversation's `AIUIHost`, and a reply whose `ai_ui` document is in the `openui` format shows its UI in place of its text.

```kotlin
val ui = AIUIHost(
    renderers = listOf(OpenUIRenderer(instructions = "Answer travel questions with UI.")),
    components = listOf(placeCard), // the app's components, placeable as `PlaceCard(...)`
    tools = listOf(calendar),       // what `Query()` and `Mutation()` run, on the device
) { action ->
    viewModelScope.launch { channel.sendMessage(Message(text = action.label, extraData = action.customData)) }
}

AIConversation(messages = messages, ui = ui)
ui.capabilities // the fence and the system prompt, with the app's components and tools, for the agent's backend
```

The system prompt starts with the app's `instructions`, then OpenUI's own, which list the app's components and describe each of its tools with its `description`, the arguments of its `inputSchema` and whether it `isReadOnly`, with the `Query()` and `Mutation()` sections that run them.

A `Query` runs by itself as the reply shows, so it runs only a read-only tool; a tool that changes something runs only from a `Mutation` the person starts with a tap, such as a button's `@Run`. A `Query` on such a tool doesn't run it: it keeps its default data and reports an `OpenUIError`.

Each reply keeps its own runtime while the host is kept, so its forms and `$variables` survive scrolling, and its state is kept with the host's state for the reply, without what password fields hold, which never reaches the agent either. What the person does that is for the agent reaches the host's `send` as an `AIUIAction` named after OpenUI's action (`continue_conversation`, or one of the library's custom actions), with the action's `context`, its other `params`, the `form` and the form's `values` in its payload. An app component's events carry its OpenUI name under `component`. Links open through the host, which opens web and email links unless the app sets other `linkSchemes`. An app component whose OpenUI name the library already has is left out, so it never replaces one of OpenUI's own. Problems with a reply's program reach `onError` as an `OpenUIError` once the reply is complete, and the log without one.

## Libraries and the theme

`openuiChatLibrary` (every answer is one `Card`) and `openuiLibrary` (a `Stack` for full-screen surfaces) pair the libraries of `@openuidev/react-ui` 1.0 with Compose components that draw a response natively. Each brings its own examples and rules for the prompt, and `componentNames` lists what it has.

Restyle a component with `replacingView`, which keeps its props and prompt; the view gets the component's `ComponentRenderProps`, with its `props`, `isStreaming`, `RenderProp` for a prop that holds components, and `DefaultView` for the library's own view of it. Drop components with `removing`; they also leave every slot that takes several types.

```kotlin
val library = openuiChatLibrary
    .replacingView("Button") { props -> Box(Modifier.padding(4.dp)) { props.DefaultView() } }
    .removing(setOf("Carousel"))
OpenUIRenderer(library = library)
```

The theme derives from `MaterialTheme`; wrap content in `ProvideOpenUITheme(theme)` to change it. Its texts are Android string resources named `stream_ai_openui_*`, which an app overrides or translates like its own.

## How it works

The language runtime (package `io.getstream.chat.android.ai.openui.lang`) is ported from upstream's TypeScript `@openuidev/lang-core` 1.0 and follows the OpenUI Lang 1.0 specification; the component libraries and the system prompt (package `io.getstream.chat.android.ai.openui.library`) follow `@openuidev/react-ui` 1.0. Both are internal and tested against upstream with conformance fixtures generated by that implementation.

- Parsing: the entry statement is `root`. Without one, the first statement that calls the library's root component renders, with a `no-root` warning; with neither, nothing renders. While a response streams, the parser only re-parses the statement that is still growing, and a `$name` at the very end of the text isn't declared until the stream ends. An edit-mode answer, with only the statements that changed, applies to the previous program.
- Values follow JavaScript semantics, because the reference implementation is TypeScript: `undefined` is a Kotlin `null`, and conversions (number formatting, `Number()`, truthiness) follow JavaScript's. Model output can't crash the parser: nesting or chains deeper than any real program, and references that would expand past any real program's size, read as `null`, and non-finite numbers serialize as `null`.
- Evaluation resolves `$variables`, references, `@` built-ins such as `@Count` and `@Each`, the library's own functions, and expressions, within a shared budget of work. A function's arguments and result are checked against its schema; a call with invalid arguments, or one that throws, is `null` and reports a runtime error. Actions evaluate to plans of steps (`@ToAssistant`, `@OpenUrl`, `@Set`, `@Reset`, `@Run` and the library's own actions); only real calls make custom steps, so data can't pose as one.
- Each response keeps its own state: `$variables`, form values and the results of `Query()` and `Mutation()`. Queries start when streaming ends and refresh at most every five seconds, whatever interval the model writes. A tool is told whether the person asked for it: a `Query` runs by itself as the UI shows, a `Mutation` from a tap. Form fields validate with the rules the model writes. Responses are stored in the OpenUI 1.0 message protocol, with their state, and messages in the older XML envelope still read.
- Libraries: the chat library (every answer is one `Card`) and the standard library (a `Stack` for full-screen surfaces) are defined like upstream's 1.0 libraries, each with the examples and rules upstream gives it. The system prompt lists the components' signatures and descriptions, how they're grouped, the library's functions and actions, and the tools `Query()` and `Mutation()` can run.
- Components are Compose views that follow the response as it streams. Only web and email links open, since the model writes every link. Images load only from public hosts, each redirect checked the same way, at about the size they show at.
- Forms validate their fields with the rules the model writes, and a form's submit button sends its values with the action. Sliders, text areas and the other fields keep the numbers the model writes within what they can draw.
- Card blocks: text, icon and image rows, metric indicators, and the snippet, overview, context, composite and visual card blocks, whose item actions carry the tapped card's details. Gaps and image sizes stay within bounds, whatever the model writes.
- Charts are drawn with Compose Canvas, without a chart library; values a chart can't draw are left out of bar, line, area, radar and scatter charts, and pie, radial and single stacked bar charts keep such a slice in their legend with the value 0.
- Icons: the lucide names OpenUI uses map to Material icons, from `material-icons-core` where it has them and otherwise from copies of just the `material-icons-extended` icons the table uses. Markdown renders with `multiplatform-markdown-renderer`, the renderer `stream-chat-android-ai-compose` uses.

## Known limitations

These follow upstream 1.0.1 as-is:

- Applying an edit-mode answer ends a statement at every top-level newline, so a ternary written over several lines loses its branches.
- Applying an edit-mode answer keeps its comments, so a commented-out `# title = ...` replaces `title` with a line that parses to nothing.
- Applying an edit-mode answer keeps every `$state` variable but drops statements that only a `$state` initializer references.
- Validation errors in a `$state` initializer are reported against the entry statement rather than the `$state` declaration.
